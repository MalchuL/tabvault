## 1. Резюме

Расширение для Chrome для хранения вкладок (Inbox / вложенные группы / теги), спроектированное так, чтобы AI-агенты могли надёжно читать, изменять и заполнять это хранилище через локальный MCP-сервер. Главное отличие от аналогов (Supatabs, OneTab, Tab Group Manager) — не UI, а **контракт данных**: строгая версионированная JSON-схема, подробные ошибки валидации вместо тихого падения, детерминированный Markdown-экспорт и семантический поиск по сохранённым вкладкам.

### 1.1 Проблема, которую решаем

Существующие тул-менеджеры вкладок (Supatabs и аналоги) проектировались для человека: экспорт/импорт — второстепенная фича, парсер падает без объяснений при малейшем отклонении формата, версии схемы не разделены. Для агентного использования это критично: агент должен **программно понимать, почему импорт не прошёл**, и иметь возможность чинить свой вывод итеративно, а не гадать.

### 1.2 Пользователи

- **Основной**: сам разработчик — технический пользователь, работающий с локальными AI-агентами (Ollama, Claude Code, Cursor и т.п.), которому нужно, чтобы агент мог сохранять/искать/раскладывать вкладки как часть рабочего процесса.
- **Вторичный**: AI-агент как «пользователь» API — важно закладывать UX ошибок и документацию именно для агента-потребителя (машиночитаемые коды ошибок, JSON Schema, примеры).

## 2. Цели и не-цели

### Цели
- Надёжное, предсказуемое хранение вкладок: Inbox → вложенные группы → теги.
- Формат данных, который агент может писать/читать без обращения к человеку за уточнением структуры.
- Импорт, который либо проходит полностью, либо даёт точный, лишённый догадок отчёт об ошибке (номер элемента/строки, что ожидалось, что получено, как исправить).
- MCP-сервер как основной интерфейс для агентов, с локальным HTTP-сервером как хранилищем истины.
- Семантический поиск по сохранённым вкладкам (title/note) через легковесную on-device модель эмбеддингов.

### Не-цели (на этом этапе)
- Синхронизация между разными физическими машинами «из коробки» — сервер локальный, репликация не рассматривается.
- Мобильные браузеры / Firefox / Safari — только Chrome (MV3).
- Совместная работа нескольких пользователей над одним хранилищем (multi-tenant).
- Полнотекстовая индексация содержимого страниц (только title/url/note/tags на старте).

## 3. Архитектура системы

```
┌─────────────────────┐        WebSocket (localhost)       ┌──────────────────────┐
│  Chrome Extension    │ ◄─────────────────────────────────► │  Local HTTP/WS Server │
│  (MV3, UI, storage    │                                     │  (источник истины:    │
│   proxy, drag&drop)   │                                     │   JSON store + Zvec)  │
└─────────────────────┘                                     └───────────┬──────────┘
                                                                          │ stdio / HTTP
                                                                          ▼
                                                              ┌──────────────────────┐
                                                              │   MCP Server          │
                                                              │  (stdio, настраиваемый │
                                                              │   на custom URL сервера)│
                                                              └───────────┬──────────┘
                                                                          │ MCP protocol
                                                                          ▼
                                                                    AI-агент
                                                                (Claude/Cursor/etc.)
```

**Ключевое решение:** источник истины — **не** `chrome.storage`, а маленький локальный сервер (Node.js или Python, TBD на этапе tech spec). Расширение — «толстый клиент» этого сервера: рисует UI, отправляет команды, кеширует для offline. MCP-сервер — отдельный процесс, который общается с локальным сервером по HTTP/WebSocket и может быть настроен на **произвольный URL** (не обязательно `localhost`), что позволяет агенту работать с хранилищем, поднятым на другой машине в локальной сети.

Такая топология (extension ↔ WebSocket ↔ localhost-сервер ↔ stdio MCP) — устоявшийся паттерн в этом классе инструментов, используется, например, в chrome-mcp и Browser MCP [web:38][web:39][web:34]. Все сетевые listener'ы по умолчанию биндятся на `127.0.0.1`, наружу ничего не торчит, если явно не сконфигурировано иное [web:38].

### 3.1 Компоненты

| Компонент | Технология (предложение) | Ответственность |
|---|---|---|
| Chrome Extension | MV3, TypeScript, React (popup/side panel) | UI, drag-n-drop, захват вкладок, кеш для offline-режима |
| Local Server | Node.js/Fastify или Python/FastAPI | Хранение JSON, валидация, версионирование, REST API |
| Vector Store | **Zvec** (embedded, без отдельного сервиса) [web:18][web:20] | Семантический поиск |
| Embedding Model | **deepvk/USER-bge-m3 ONNX INT8** (~347 MB, RU+EN, CPU) [web:35] | Генерация векторов для title/note |
| MCP Server | Node.js, `@modelcontextprotocol/sdk`, stdio-транспорт | Экспонирует tools агенту, проксирует к Local Server по настраиваемому URL |

Учитывая, что ты уже используешь FastAPI и Ollama в стеке — Python/FastAPI для Local Server и Ollama-совместимый embedding-раннер выглядят органичнее, чем Node.js; финальный выбор — на этапе tech spec.

## 4. Модель данных

### 4.1 Сущности

- **Tab** — атомарная ссылка: `id, url, title, favicon, note?, tags[], groupId, position, createdAt, updatedAt`.
- **Group** — контейнер, может быть вложенным: `id, name, parentId?, color?, position, createdAt, updatedAt`.
- **Inbox** — не отдельная сущность, а **зарезервированный `groupId = null` / `"inbox"`**: буфер для только что сохранённых вкладок до разбора по группам.
- **Tag** — свободная строка + опциональное описание: хранится отдельным справочником `{ name, description?, createdAt }`, чтобы можно было **зафетчить список тегов как Markdown** (см. §5.3). Tab хранит только массив `tags: string[]` — многие-ко-многим, без exclusivity (в отличие от групп).

### 4.2 Инварианты

- `id` — стабильный UUID v4, никогда не меняется и не переиспользуется.
- `Group.parentId` образует дерево; циклы запрещены и проверяются при каждой записи.
- Дедупликация по `url` (нормализованному — без trailing slash, без tracking-параметров по настраиваемому списку) — при импорте и при обычном сохранении, с явной опцией «объединить» (слить теги/note) vs «пропустить».
- `note`/`summary` и `updatedAt`/`createdAt` — оба помечены как **опциональные к выдаче**: любой read/export endpoint принимает флаг вроде `fields=minimal` для ответа без них (агенту не всегда нужен полный объект — экономия токенов).

## 5. Формат данных: JSON + Markdown

### 5.1 Основной формат — JSON (источник истины)

Отказались от JSONL в пользу обычного JSON — вложенные группы естественнее выражаются деревом/списком с `parentId`, чем построчным логом, а количество вкладок у одного пользователя не настолько велико, чтобы требовать streaming-парсинга.

```json
{
  "schemaVersion": 1,
  "exportedAt": "2026-08-17T10:22:00Z",
  "tags": [
    { "name": "work", "description": "Рабочие задачи", "createdAt": "2026-08-01T00:00:00Z" },
    { "name": "read-later", "description": null, "createdAt": "2026-08-01T00:00:00Z" }
  ],
  "groups": [
    { "id": "g-1", "name": "Research", "parentId": null, "color": "#4285F4", "position": 0,
      "createdAt": "2026-08-01T00:00:00Z", "updatedAt": "2026-08-10T00:00:00Z" },
    { "id": "g-2", "name": "LLM papers", "parentId": "g-1", "color": null, "position": 0,
      "createdAt": "2026-08-02T00:00:00Z", "updatedAt": "2026-08-02T00:00:00Z" }
  ],
  "tabs": [
    {
      "id": "t-1001",
      "url": "https://arxiv.org/abs/2508.01234",
      "title": "Flow Matching for Generative Modeling",
      "favicon": "https://arxiv.org/favicon.ico",
      "note": "Перечитать раздел про ODE solvers",
      "tags": ["read-later"],
      "groupId": "g-2",
      "position": 0,
      "createdAt": "2026-08-02T09:00:00Z",
      "updatedAt": "2026-08-02T09:00:00Z"
    }
  ]
}
```

### 5.2 Две операции импорта (без разделения внутри самого JSON)

Формат файла один и тот же для обеих операций — режим выбирается **при загрузке**, не кодируется в структуре:

- **Replace (restore from backup)** — полностью заменяет всё хранилище (или явно выбранное поддерево группы, если импорт запущен «в контексте» конкретной группы) присланным содержимым. Деструктивная операция → требует подтверждения в UI и создаёт автоматический backup предыдущего состояния перед заменой.
- **Upload (merge/append)** — добавляет новые сущности и обновляет существующие по `id` (upsert), не трогая остальное хранилище. Дубликаты по `url` обрабатываются по правилам дедупликации (§4.2).

### 5.3 Markdown — второй формат импорта/экспорта

Грамматика — в духе Supatabs, с метаданными на отдельной строке под ссылкой (человекочитаемо, парсится регуляркой без YAML):

```markdown
## Research

### LLM papers

- [Flow Matching for Generative Modeling](https://arxiv.org/abs/2508.01234)
  id: t-1001
  tags: read-later
  note: Перечитать раздел про ODE solvers
  createdAt: 02/08/2026
  updatedAt: 02/08/2026

## Inbox

- [Some quick save](https://example.com)
  id: t-1002
  tags:
  note:
  createdAt: 17/08/2026
  updatedAt: 17/08/2026
```

Правила:
- Вложенность групп — через уровень заголовка (`##` = корневая группа, `###` = дочерняя, и так далее); группы без родителя — `##`, Inbox — зарезервированный раздел `## Inbox`.
- Метаданные — plain-текстом на следующей строке после ссылки, формат `key: value`, дата — `DD/MM/YYYY` (как ты указал).
- Favicon **не** экспортируется в Markdown (не несёт смысла для человека/агента, читающего текст) — восстанавливается автоматически при следующей синхронизации через `chrome://favicon` или fetch на импортированный URL.
- Markdown — **lossy** по времени (без секунд) и предназначен для чтения/быстрой правки человеком или агентом в чате; JSON остаётся единственным источником истины для точного бэкапа.
- Отдельный **справочник тегов** может быть отфетчен как самостоятельный Markdown-документ:

```markdown
# Tags

- **work** — Рабочие задачи
- **read-later** — _(без описания)_
```

### 5.4 JSON Schema

Публикуется как отдельный `.json` файл, версионированный вместе со схемой (`schema/v1.tabvault.schema.json`), чтобы агент мог валидировать свой экспорт до отправки на сервер (`ajv` или аналог на стороне агента/сервера).

## 6. Версионирование и обратная совместимость

- Каждый экспортированный документ содержит `schemaVersion: <int>`.
- **Отдельный парсер на каждую версию схемы** — `parsers/v1.ts`, `parsers/v2.ts`, без попытки писать один «универсальный» парсер со ветвлениями внутри. При добавлении v2 пишется мигратор `migrateV1toV2()`, старые файлы продолжают парситься их собственным парсером, затем приводятся к последней версии внутри.
- Импорт документа с `schemaVersion`, которого сервер не знает (выше текущей) → явная ошибка `E_UNKNOWN_SCHEMA_VERSION` с указанием, какие версии поддерживаются — **не** попытка угадать структуру.
- Обратная совместимость гарантируется только «вниз» (новый сервер понимает все старые версии через мигратор); новый формат старым сервером осознанно не читается.

## 7. Детальная обработка ошибок (ключевое требование)

Валидация — на каждом шаге: перед записью в БД, при чтении файла импорта, при разборе Markdown. Каждая ошибка обязана содержать:

1. **Локацию** — путь до проблемного элемента (`tabs[3].url`, или для Markdown — номер строки).
2. **Что ожидалось** и **что получено** (типы/формат/допустимые значения).
3. **Машиночитаемый код** для программной обработки агентом.
4. **Человекочитаемое сообщение** с предлагаемым исправлением.
5. Импорт **не падает на первой ошибке** — собирает **все** найденные проблемы за один проход и возвращает список (агенту дешевле почитать раз и исправить пачкой, чем гонять запрос по одной ошибке).

Пример ответа при неудачном импорте:

```json
{
  "success": false,
  "errors": [
    {
      "code": "E_INVALID_URL",
      "path": "tabs[3].url",
      "expected": "valid absolute URL (http/https)",
      "received": "example.com/page",
      "message": "URL должен начинаться с http:// или https://. Похоже, отсутствует протокол.",
      "suggestedFix": "https://example.com/page"
    },
    {
      "code": "E_DUPLICATE_ID",
      "path": "tabs[7].id",
      "expected": "unique id across document",
      "received": "t-1001",
      "message": "id 't-1001' уже использован в tabs[0]. Каждый id должен быть уникален в пределах документа.",
      "suggestedFix": "Сгенерировать новый UUID для tabs[7] или использовать этот id только для upsert существующей записи."
    },
    {
      "code": "E_UNKNOWN_SCHEMA_VERSION",
      "path": "$.schemaVersion",
      "expected": "one of [1, 2]",
      "received": 5,
      "message": "Схема версии 5 не поддерживается этим сервером (максимум — 2).",
      "suggestedFix": "Экспортировать данные в поддерживаемой версии схемы, либо обновить сервер."
    }
  ],
  "warnings": [
    { "code": "W_ORPHAN_TAG", "path": "tabs[2].tags[0]", "message": "Тег 'archived' не найден в справочнике tags — будет создан автоматически." }
  ]
}
```

Полный реестр кодов ошибок (`E_INVALID_URL`, `E_MISSING_REQUIRED_FIELD`, `E_INVALID_DATE_FORMAT`, `E_CYCLIC_GROUP_REFERENCE`, `E_DUPLICATE_ID`, `E_UNKNOWN_SCHEMA_VERSION`, `E_MARKDOWN_PARSE_ERROR` и т.д.) — отдельный раздел в tech spec, живёт как машиночитаемый JSON-каталог рядом с кодом (не просто в документации), чтобы клиент/агент мог сверяться программно.

## 8. MCP-сервер: инструменты для агента

Полный набор операций — без урезания под MVP:

| Tool | Назначение |
|---|---|
| `list_tabs` | Список вкладок с фильтрами (group, tag, inbox), поддержка `fields=minimal|full` |
| `search_tabs` | Семантический + текстовый поиск по title/note |
| `get_tab` | Полная информация по одной вкладке |
| `save_tab` / `save_tabs` | Сохранить одну/несколько ссылок (в Inbox по умолчанию) |
| `update_tab` | Изменить title/note/tags/group/position |
| `delete_tab` | Удалить вкладку |
| `move_tab` | Переместить между группами / изменить порядок |
| `create_group` / `update_group` / `delete_group` | Управление вложенными группами |
| `list_groups` | Дерево групп |
| `add_tag` / `remove_tag` / `list_tags` | Управление тегами и их описаниями |
| `export_data` | Экспорт в JSON или Markdown (полный или по фильтру группы/тега) |
| `import_data` | Импорт в режиме `replace` или `upload`, возвращает подробный отчёт (§7) |

MCP-сервер конфигурируется URL-адресом Local Server (по умолчанию `http://127.0.0.1:<port>`, но переопределяемо), что отделяет «мозги» протокола MCP от «хранилища» — агент может быть настроен на удалённый инстанс в локальной сети без переустановки MCP-сервера.

## 9. Семантический поиск

- **Векторная БД**: Zvec — embedded, без отдельного процесса/докера, работает как библиотека внутри Local Server [web:18][web:20][web:21].
- **Модель эмбеддингов**: `deepvk/USER-bge-m3` в ONNX INT8-квантизации — мультиязычная (RU/EN), CPU-only, ~347 MB, без CUDA [web:35][web:32]. Разумный fallback для более скромного железа — `all-MiniLM-L6-v2` (только английский, ~100 MB) [web:25], но раз рабочий язык — русский, стоит сразу закладывать bge-m3.
- **Индексируется**: `title + note`. URL контента страниц не скрейпится на этом этапе (см. §2, не-цели) — можно вынести в будущую версию как опциональный «deep index».
- Эмбеддинг пересчитывается при создании/изменении `title` или `note`; хранится вместе с `tabId` в Zvec-индексе, отдельно от основного JSON-хранилища (может быть перестроен с нуля из основного стора при необходимости — невосстанавливаемых данных в векторной БД не держим).

## 10. UI и взаимодействие (расширение)

- Side panel или popup, структура: Inbox (сверху, как временная зона) → дерево вложенных групп → внутри группы список вкладок.
- **Drag-n-drop**: перетаскивание вкладок между группами (включая вложенные), изменение порядка внутри группы — как в Supatabs.
- Быстрый захват: hotkey на сохранение текущей/всех вкладок в Inbox, с опцией направленного захвата (влево/вправо/все), аналогично Supatabs.
- Индикатор состояния соединения с Local Server (расширение — тонкий клиент, должен явно показывать «сервер недоступен», а не тихо терять изменения).
- Поиск в UI — тот же семантический движок, что и для агента (единая логика, не дублируется).

## 11. Развёртывание Local Server

Так как источник истины — маленький локальный сервер, а не `chrome.storage`, потребуется подробный гайд разворачивания:

- Docker-образ «из коробки» (учитывая, что ты предпочитаешь self-hosted/Docker) с volume для персистентности JSON-хранилища и Zvec-индекса.
- Альтернатива без Docker — единичный бинарник/скрипт (`pip install` + `uvicorn` при FastAPI, либо `npm install` при Node) с однострочным запуском.
- Явная секция в документации: как расширение находит сервер (порт по умолчанию + возможность указать кастомный URL в настройках расширения), как MCP-сервер находит тот же URL (переменная окружения/конфиг-файл), и что нужно для доступа с другой машины в локальной сети (bind-адрес, но без выхода в открытый интернет — сервер не рассчитан на публичный доступ без дополнительной аутентификации).

## 12. Открытые вопросы к следующей итерации (tech spec)

- Стек Local Server: Node.js/Fastify vs Python/FastAPI (учитывая совместимость с ONNX Runtime и твой существующий стек — FastAPI выглядит естественнее).
- Точный список полей `Group.color` — фиксированная палитра (как Chrome tab groups) или произвольный hex?
- Аутентификация Local Server ↔ MCP-сервер, если сервер поднят не на localhost (токен/API key в конфиге MCP).
