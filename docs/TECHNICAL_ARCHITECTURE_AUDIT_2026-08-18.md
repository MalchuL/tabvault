# TabVault Technical Architecture Audit

**Author:** Manus AI  
**Assessment date:** 18 August 2026  
**Assessment type:** Source-based architecture, security, scalability, maintainability, and delivery-process review. This is not a penetration test or an infrastructure configuration review.

## Executive assessment

TabVault has a clear product direction: a React workspace and Chrome extension provide a local-first library, FastAPI provides an optional shared API and semantic search, and an MCP bridge exposes the same library to agents. The application has useful quality foundations—formatting, linting, type checks, a production build, and 14 browser workflows—but its current implementation is suitable only for a **trusted single-user/local deployment**. It is not yet safe or robust enough to expose as a multi-user or Internet-facing service.

The highest risks are a public-server default credential path, overly broad CORS and extension host privileges, file-backed whole-document persistence without concurrency control, and synchronous semantic indexing on write and search paths. The most valuable architectural investment is therefore not another UI feature: it is establishing secure identity, a transactional persistence boundary, and asynchronous indexing/sync processing.

> **Security position:** no durable service secret should be compiled into frontend or extension code. A static browser application cannot safely hold a server-wide bearer secret. Replace the shared `admin` key model with server-issued, scoped, revocable credentials and a backend-controlled identity flow.

## Scope and evidence

The audit reviewed the React/Vite application, Chrome MV3 extension, browser persistence adapter, FastAPI server, file-backed semantic index, in-process health scheduler, TypeScript MCP bridge, package manifests/lockfiles, build configuration, and automated tests. Concrete references below identify current code locations. The package scan executed during this audit reported **16 high**, **33 moderate**, and **4 low** production dependency advisories in the main package; the MCP package reported no production advisories. The application quality suite and 14 Playwright workflows were previously passing, but they do not exercise the most important API, extension, concurrency, or security boundaries.

| System boundary       | Current implementation                                                                                   | Primary consequence                                                                                                           |
| --------------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Browser and extension | React app writes a complete library and API configuration into `localStorage` or `chrome.storage.local`. | Fast offline behavior, but browser-side key storage and whole-document synchronization enlarge compromise and conflict scope. |
| API                   | FastAPI process with one static bearer key, JSON-file persistence, and optional Ollama embeddings.       | Simple deployment, but no tenancy, transaction isolation, rate controls, or horizontal-scale safety.                          |
| Semantic index        | JSON vectors rebuilt synchronously through local HTTP embedding calls.                                   | Meaning search works locally, but write and query latency rises with library size and provider failures.                      |
| MCP                   | Thin stdio proxy forwarding 19 tools to the same API.                                                    | Useful agent access, but destructive actions, identity, timeouts, and audit controls are inherited rather than designed.      |

## 2. Root-cause analysis

The common root cause is that a well-designed **local-first prototype boundary** is being asked to serve as a shared, public-service architecture. A single JSON document, one bearer key, synchronous side effects, and direct browser-to-API requests minimize early complexity but couple identity, storage, synchronization, and indexing into each request path.

The key architectural coupling is visible in the write path: a UI mutation updates the in-memory React document, persists a full browser snapshot, optionally imports a full document to the server, rewrites a JSON file, and then reindexes embeddings synchronously. This makes any slow provider, large import, or concurrent update a user-visible failure. The MCP bridge reproduces the API surface rather than encapsulating domain policy, so it inherits every API weakness.

The security issue is not that browser storage is inherently wrong for local data. The issue is treating a **shared server credential** as if it can be safely delivered to a browser. It cannot. A browser may hold a user/device credential, but the service must issue, scope, rotate, and revoke it; the server’s root secret remains server-side in a secret manager or protected environment.

## 3. Target architecture

The recommended target preserves TabVault’s local-first experience while separating responsibilities.

| Layer                | Target responsibility                                                                                         | Required design decision                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Client and extension | Local cache, intent capture, rendering, optimistic UI, durable operation outbox.                              | No server-wide secrets. Store only a revocable device/session credential and encrypt at-rest where platform support permits. |
| Identity and edge    | Login/device authorization, CORS allowlist, TLS, rate limits, request IDs, security headers, abuse controls.  | Use a BFF or dedicated auth service for browser clients; do not expose root API keys.                                        |
| Domain API           | Validated commands and queries, archive state machine, collection ownership, idempotency, conflict responses. | Define versioned OpenAPI/JSON schemas and use generated client contracts.                                                    |
| Persistence          | Transactional entities, revisions, audit log, backups, retention.                                             | Start with SQLite WAL for a one-host trusted deployment; use PostgreSQL for shared/public deployments.                       |
| Async workers        | Embedding, import validation, export generation, sync retries, health checks.                                 | Durable queue/outbox, bounded concurrency, retries/backoff, dead-letter handling, metrics.                                   |
| MCP gateway          | Scoped agent tools, policy/confirmation, correlation, redaction, timeouts.                                    | Separate read-only from write-capable access; enforce API domain policy rather than duplicating it.                          |

## 4. Implementation strategy

### Phase A — Contain release blockers (0–7 days)

First, prevent unsafe deployment rather than adding features. Remove `admin` fallbacks from client, extension, MCP, and public server startup. Bind to loopback by default and fail public-mode startup unless TLS termination, a strict CORS allowlist, and a non-default server secret are configured. Add rate and body limits at ingress, remove unauthenticated API documentation in public mode, and pin/remove vulnerable packages. Move pnpm overrides/patch configuration to a supported workspace configuration and prove it in CI.

Define an API contract immediately: strict Pydantic DTOs, `extra="forbid"`, field length/array limits, structured error codes, archive state transitions, pagination, and idempotency keys. Close the `restore_tabs` arbitrary-object bypass and align server URL normalization with the client/extension policy.

**Exit criteria:** external API deployment fails closed with weak/default configuration; authenticated requests work only from configured origins; dependency audit has no unapproved high advisories; API contract tests reject malformed archive, restore, and import requests.

### Phase B — Establish durable domain foundations (weeks 2–4)

Introduce a repository/service boundary before replacing all UI code. Migrate authoritative data to a transactional schema with migrations, backups, and optimistic versions. Keep the existing JSON structure as a versioned import/export adapter. Convert direct PATCH endpoints into typed domain commands and record immutable audit events for archive, restore, permanent deletion, import, group deletion, and agent-originated writes.

Build a durable sync outbox in the client and extension. Each operation needs a UUID idempotency key, entity revision, retry state, and conflict result. This allows local storage to remain useful offline without whole-library replacement writes. Implement an explicit conflict UI rather than silently choosing a winner.

**Exit criteria:** two concurrent clients cannot silently overwrite a tab; server restarts do not lose accepted operations; backup/restore is tested; active/archive uniqueness is enforced only by the server domain service.

### Phase C — Decouple expensive work and support scale (weeks 4–8)

Move semantic indexing, imports, exports, and health scheduling to workers. The API should return quickly with a job identifier and status endpoint; search should use a completed index or lexical fallback, never trigger a rebuild inline. Add quotas, timeouts, cancellation, metrics, and tracing around embedding calls. Introduce cursor pagination and virtualized UI lists, then profile target libraries of 1,000, 10,000, and 50,000 tabs.

**Exit criteria:** API write latency is independent of embedding provider latency; repeated provider failures do not consume web workers; import/export has bounded memory behavior; search and scrolling meet defined latency budgets.

### Phase D — Govern agent and extension capability (weeks 6–10)

Convert MCP from pass-through to a policy-aware adapter. Use scoped device identities, read/write separation, confirmation for destructive actions, audit events, and retries with deadlines. Reduce extension permissions to optional, user-granted origins and harden preview fetching with origin, MIME type, byte, and private-network controls. Add contract tests shared by web, extension, MCP, and API.

**Exit criteria:** every agent mutation has actor, correlation ID, idempotency key, and audit record; the extension requests only the host access the user approved; no server secret appears in browser bundles, manifests, logs, or documentation examples.

## 5. Engineering controls and verification

| Control                      | Minimum implementation                                                                                                        | Verification                                                                                             |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Identity and secret handling | Secret manager/environment injection for server secrets; device/session credentials only in clients; rotation and revocation. | Build-time secret scan, runtime startup guard, negative test proving `admin` is rejected in public mode. |
| API protection               | CORS allowlist, rate/body limits, TLS at edge, typed validation, pagination, idempotency.                                     | Automated API security tests, load test, CORS matrix, malformed payload/property tests.                  |
| Data integrity               | Database transactions, migrations, optimistic revisions, archive state machine, append-only audit events.                     | Concurrent-write tests, backup/restore drill, migration rollback test.                                   |
| Async resilience             | Outbox/queue, retries with jitter, circuit breaker, job metrics and alerts.                                                   | Provider outage simulation, retry/dead-letter test, SLO dashboard.                                       |
| Extension safety             | Optional host permissions, origin controls, bounded preview fetches, redacted logs.                                           | Manifest review, permission regression test, private-network/oversized-response test.                    |
| Delivery quality             | CI pipeline for formatting, lint, type checks, build, API/MCP/extension tests, dependency/SAST/secret scan, SBOM.             | Protected branch requires all checks and an audited exception process.                                   |

## 6. Recommended first backlog

1. Create a security hardening PR that removes default keys from shipped clients, fails closed in public mode, restricts CORS, binds loopback by default, and fixes ignored pnpm patch/override configuration.
2. Create an API-contract PR that replaces loose mutation payloads with strict DTOs, adds URL canonicalization fixtures, limits input sizes, and covers archive/restore/import invariants with API tests.
3. Create a persistence decision record and migration spike: SQLite WAL for single-host versus PostgreSQL for shared deployment, including schema, revision strategy, backup plan, and data migration rehearsal.
4. Create an asynchronous indexing/outbox spike with target latency budgets and provider-failure behavior before adding more semantic-search features.
